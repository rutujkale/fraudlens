# FraudLens — Financial Transaction Risk Intelligence Platform

## Complete Project Specification

**Project type:** End-to-end Machine Learning + Data Engineering + Risk Analytics + Explainable AI + Decision Intelligence

**Primary domain:** Financial transaction fraud detection and risk scoring

**Primary objective:** Build a defensible, realistic, end-to-end fraud-risk intelligence platform that generates behavioral transaction data, stores it in PostgreSQL, creates point-in-time features without data leakage, trains and evaluates machine-learning models under realistic class imbalance and temporal drift, optimizes intervention thresholds using business cost and analyst capacity, adds an anomaly-detection experiment for unseen fraud, explains predictions with SHAP, and exposes the final model through a FastAPI + Streamlit application.

**Core philosophy:**

> Do not build a model merely to classify transactions. Build a decision system that answers whether a transaction deserves approval, additional verification, manual review, or a hold, while making the trade-offs visible and measurable.

---

# 1. Executive Summary

Financial transaction fraud detection is not simply a binary classification problem. In a real operational setting, fraud is rare, legitimate transactions can look unusual, fraud patterns evolve, customer behavior is highly heterogeneous, and every false positive can create friction or operational cost while every false negative can produce financial loss.

FraudLens is designed around that reality.

The project will simulate a financial ecosystem containing customers, accounts, devices, merchants, locations, transactions, and fraud events. The simulation will intentionally include noise, overlapping behavior between legitimate and fraudulent transactions, difficult legitimate cases, multiple fraud patterns, and concept drift over time. This prevents the model from learning trivial rules such as “new device + high amount = fraud.”

The generated data will be stored in PostgreSQL. A reusable point-in-time feature engineering layer will derive customer behavioral, temporal, velocity, device, geographic, and transaction-deviation features. Automated tests will verify that features never use information from the future transaction or future observation window.

Three primary decision approaches will be evaluated:

1. A transparent rule-based baseline.
2. Logistic Regression as an interpretable machine-learning baseline.
3. XGBoost as the main supervised tabular model.

An Isolation Forest experiment will be used separately to study whether unsupervised anomaly information improves detection of fraud patterns that were not represented in supervised training.

Model evaluation will use temporal splits rather than random splits. Performance will focus on precision-recall metrics and operational measures rather than misleading raw accuracy. Probability calibration will be performed before converting probabilities into a user-facing risk score.

The central differentiator is **cost-based decision optimization**. Instead of selecting a threshold because it maximizes F1, the system will model fraud losses, false-positive costs, investigation capacity, and transaction value. It will determine the policy that minimizes expected operational/business loss under realistic constraints.

The final system will expose transaction scoring through FastAPI and a Streamlit application. A user will be able to enter a transaction or upload a batch, receive a calibrated risk score, see the recommended action, inspect SHAP-based reasons, view the review queue, and inspect model-performance and drift dashboards.

The final portfolio artifact should tell a complete story:

```text
Problem definition
      ↓
Behavioral data simulation
      ↓
PostgreSQL data model
      ↓
Point-in-time feature engineering
      ↓
Leakage tests
      ↓
Rules baseline
      ↓
Logistic Regression
      ↓
XGBoost
      ↓
Temporal evaluation
      ↓

      ↓

      ↓

      ↓

      ↓

      ↓

      ↓

```

# 2. Why This Project Exists

Most student fraud projects stop at:

```text
CSV
 ↓
EDA
 ↓
XGBoost
 ↓
99% accuracy
 ↓
Streamlit
```

That format creates several credibility problems:

- The fraud labels may have been generated by simplistic rules.
- Random train/test splitting may leak customer behavior across both sets.
- Feature engineering may accidentally include future information.
- Accuracy can be meaningless with extreme class imbalance.
- The model may perform well only on the synthetic data distribution.
- A probability such as 0.87 may not be calibrated.
- There is no explanation of what action a business should take.
- There is no relationship between model threshold and financial cost.
- There is no evidence that the system survives changing fraud patterns.

FraudLens is explicitly designed to address those weaknesses.

The project should look less like a Kaggle notebook and more like a small research-and-engineering prototype for a fraud analytics team.

# 9. Data Generation Philosophy

The simulator is one of the most important components of the entire project.

It must **not** be a simple row generator that follows deterministic fraud rules.

The simulator should represent three layers:

1. **Customer behavior** — what each customer normally does.
2. **Random behavioral variation** — legitimate behavior is not perfectly predictable.
3. **Fraud intervention** — fraudulent activity is generated as a noisy, overlapping deviation from normal behavior.

The generated data should be difficult enough that a model has to combine multiple signals.

---

# 10. Customer Population

The simulator should support a configurable number of customers.

Recommended initial scale:

- 50,000–250,000 customers;
- configurable through YAML/configuration;
- enough transactions to create meaningful time-based behavior.

A smaller development mode should also exist, for example:

```text
customers: 5,000
transactions: ~250,000
period: 180 days
```

The full benchmark can then be generated after the simulator is validated.

## 12.3 High-Spend Customer

- High transaction velocity.

# 13. Normal Transaction Generation

A normal transaction should be sampled from the customer’s own behavioral distribution.

Important dimensions:

### Amount

Use a skewed distribution rather than a uniform random number.

Possible approach:

- log-normal or gamma distribution;
- customer-specific mean and variance;
- occasional legitimate outliers.

### Time

Use customer-specific active-hour distributions with noise.

### Merchant

Sample from preferred categories while occasionally allowing less-common categories.

### Location

Sample around a home region or travel pattern.

### Device

Use known devices with occasional legitimate device changes.

### Frequency

Use a customer-specific rate with day-to-day variability.

---

# 14. Hard Negatives

Hard negatives are essential.

They are legitimate transactions that intentionally resemble fraud.

Examples:

## Holiday purchase

- Large amount.
- New merchant.
- Different location.
- Legitimate event.

## New phone

- New device.
- Same customer.
- Normal amount.
- Legitimate behavior.

## Travel

- Large location change.
- Short time gap.
- Legitimate travel window.

## Large medical bill

- Very large transaction.
- Rare category.
- Legitimate.

## Emergency purchase

- Unusual hour.
- Higher amount.
- Legitimate.

These cases force the classifier to reason over combinations of signals rather than memorizing one indicator.

---

# 15. Fraud Event Generation

Fraud should be generated using probabilities and combinations of signals.

Avoid rules such as:

```text
IF new_device AND amount > threshold
THEN fraud
```

Instead:

```text
fraud_probability = base_rate
                  + amount_deviation_effect
                  + velocity_effect
                  + device_effect
                  + geographic_effect
                  + temporal_effect
                  + interaction_effect
                  + noise
```

Then sample whether a fraud event occurs.

This produces overlap between legitimate and fraudulent distributions.

# 17. Fraud Prevalence

Fraud prevalence should be intentionally low.

Recommended development range:

- approximately 0.2%–1.0% overall fraud;
- configurable by simulation period;
- additional stress tests at different prevalence levels.

The exact prevalence should not be selected merely to produce convenient model scores.

The final README must report the actual prevalence used in each experiment.

---

# 18. Concept Drift

Concept drift is required for the advanced experiment.

Example:

### Period A — Early fraud strategy

Fraud is more likely to involve:

- new devices;
- large transaction amounts;
- obvious geographic anomalies.

### Period B — Later fraud strategy

Fraud becomes more subtle:

- known devices;
- smaller transactions;
- normal locations;
- structuring;
- moderate velocity.

The model is trained on earlier observations and evaluated on later observations.

Expected outcome:

> Performance should degrade when the underlying fraud strategy changes.

That is a useful finding rather than a failure.

# 22. Point-in-Time Feature Engineering

This is one of the most important technical requirements.

For a transaction occurring at time `T`, any feature must be computed only from transactions with timestamps `< T`.

Incorrect:

```text
avg_amount = average(all customer transactions)
```

This uses future information when the feature is calculated for historical rows.

Correct:

```text
avg_amount_before_T = average(customer transactions where timestamp < T)
```

# 24. Leakage Prevention

The project must contain automated tests for feature leakage.

## Leakage rule

For every transaction at time `T`, no feature can reference:

- the current transaction outcome;
- future transactions;
- future customer behavior;
- future fraud labels;
- future activity aggregates.

## Suggested tests

### Test 1 — Future timestamp exclusion

Verify that every source record used for a transaction feature has timestamp `< T`.

### Test 2 — Current row exclusion

Ensure the current transaction itself is not included in rolling customer statistics.

### Test 3 — Post-transaction count exclusion

Ensure `transaction_count_24h` does not count transactions after `T`.

### Test 4 — Future label exclusion

Ensure no target-derived field enters training features.

### Test 5 — Train/test time boundary

Ensure no training feature is calculated using data after the train cutoff.

These tests should be executed in CI.

# 25. Train / Validation / Test Strategy

Never use a naive random split as the primary evaluation.

Recommended structure:

```text
Historical time ────────────────────────────────►

TRAIN                  VALIDATION              TEST
|-------------------|  |------------------|   |----------------|
Earlier period         Threshold/model tuning   Final future period
```

Example:

- Train: first 60%
- Validation: next 20%
- Test: final 20%

The exact dates should be determined after data generation.

---

# 26. Group-Aware Validation

A separate experiment should test generalization to new customers.

Two evaluation settings are useful:

### Setting A — Same-customer future behavior

Train and test may contain the same customer, but different time periods.

This resembles ongoing monitoring of known customers.

### Setting B — Customer holdout

Some customers are completely excluded from training.

This tests generalization to previously unseen customer behavior.

Both results should be reported separately because they answer different business questions.

# 31. Why Accuracy Is Not the Primary Metric

At low fraud prevalence, a classifier can achieve very high accuracy while missing most fraudulent transactions.

Therefore, the main metrics are:

- PR-AUC;
- precision;
- recall;
- F1;
- recall at fixed precision;
- recall@top-K;
- false positive rate;
- expected financial loss.

Accuracy may still be shown for completeness but should never be the headline metric.

---

# 32. PR-AUC

Precision-recall curves are especially useful when the positive class is rare.

The project should report PR-AUC for:

- Rules baseline where applicable;
- Logistic Regression;
- XGBoost;
- XGBoost + anomaly score.

Confidence intervals should optionally be generated using bootstrap resampling.

# 33. Recall at Fixed Precision

A useful operational question is:

> If fraud analysts need a high-confidence review queue, how much fraud can the model capture while maintaining a minimum precision?

Example analysis:

```text
At 90% precision → recall = X%
At 80% precision → recall = Y%
At 70% precision → recall = Z%
```

Actual values must come from the experiment.

---

# 34. Recall@Top-K

In operational settings, the fraud team may only have capacity to review a small number of transactions.

Define `K` as the percentage of transactions that can be reviewed.

Examples:

- top 0.5%;
- top 1%;
- top 2%;
- top 5%.

Metric:

```text
Recall@Top-K = fraud captured within the top K ranked transactions
             / total fraud in the evaluation set
```

This directly connects model ranking to analyst capacity.

---

# 35. Probability Calibration

A model probability is not automatically a trustworthy probability.

If a model outputs `0.80`, we want transactions with predicted probability near 0.80 to actually contain fraud at approximately that rate, subject to sampling and calibration assumptions.

Candidate calibration approaches:

- Platt scaling / sigmoid calibration;
- isotonic regression.

Calibration must be performed on a validation set without touching the final test labels.

Suggested evaluation:

- reliability diagram;
- Brier score;
- expected calibration error;
- before/after calibration comparison.

---

# 36. Risk Score

After calibration, map the probability into a user-facing risk score.

For example:

```text
risk_score = round(calibrated_probability × 100)
```

This means:

- 0–29: LOW
- 30–69: MEDIUM
- 70–89: HIGH
- 90–100: CRITICAL

However, the score categories are presentation labels, not scientific truths. The final action thresholds are chosen separately through business-cost optimization.

---

# 37. Cost Model

The cost model is the central business component.

For each transaction, estimate:

## False Negative Cost

A fraudulent transaction that is incorrectly approved.

Possible formulation:

```text
FN_cost = transaction_amount × fraud_loss_rate
```

## False Positive Cost

A legitimate transaction that is incorrectly intercepted.

Possible components:

```text
FP_cost = review_cost
        + customer_friction_cost
        + estimated abandonment_cost
```

## Manual Review Cost

Every transaction sent to analysts consumes capacity.

```text
review_cost = analyst_cost_per_case
```

The exact values are configurable assumptions and must be disclosed.

---

# 38. Amount-Dependent Cost

A missed ₹80,000 fraud should not be treated as equivalent to a missed ₹800 fraud.

The expected financial loss should therefore vary with transaction amount.

Example:

```text
Expected FN loss
= P(fraud) × amount × loss_rate
```

This is more realistic than a constant “one mistake = one cost” metric.

---

# 39. Analyst Capacity Constraint

Assume analysts can investigate only a finite number of transactions each day.

Example configuration:

```text
review_capacity_per_day = 500
```

A policy that flags 5,000 transactions is operationally infeasible even if its recall looks excellent.

The optimization should therefore evaluate both:

- expected loss;
- review workload.

---

# 40. Threshold Optimization

Candidate thresholds can be scanned across a grid.

For each threshold, calculate:

- transactions flagged;
- fraud captured;
- false positives;
- false negatives;
- review load;
- fraud loss;
- review cost;
- customer friction cost;
- total expected cost.

Then select the best feasible threshold.

### Threshold B

The values must be generated from the actual experiment.

# 43. Sensitivity Analysis

Because cost assumptions are simulated, evaluate multiple scenarios.

Example:

### Scenario A — Low false-positive cost

Customer friction is relatively cheap.

### Scenario B — Balanced cost

Moderate friction and fraud-loss assumptions.

### Scenario C — High false-positive cost

Customer experience is heavily prioritized.

### Scenario D — High fraud-loss cost

Financial loss prevention is prioritized.

For each scenario, show:

- optimal threshold;
- expected loss;
- fraud recall;
- review volume.

This demonstrates that there is no universally correct threshold without business assumptions.

# 44. Isolation Forest Experiment

Isolation Forest should not simply be added because “anomaly detection is cool.”

The experiment must answer a specific question:

> **Can an unsupervised anomaly score help a supervised fraud model detect fraud patterns that were not represented in supervised training?**

---

# 45. Unseen-Fraud Experiment

Hold out one fraud scenario from supervised training.

For example:

```text
Training fraud types:
- transaction burst
- account takeover
- device compromise
- amount anomaly
- geographic anomaly
- merchant anomaly

Held-out fraud type:
- structuring
```

Train the supervised model without structuring examples.

Then test on a dataset containing structuring fraud.

Compare:

```text
XGBoost
vs.
XGBoost + IsolationForest anomaly score
```

The anomaly score should be included as an additional feature if the experiment is designed that way.

---

# 46. Interpretation of the Isolation Forest Result

Possible outcomes:

### Outcome A
No meaningful benefit.

Conclusion:

> Anomaly scoring did not provide additional value for this fraud distribution.

### Outcome B
Better recall on unseen fraud but little overall PR-AUC improvement.

This is highly interesting.

### Outcome C
Meaningful overall improvement.

Investigate why and test robustness.

The goal is not to force a positive result.

# 61. What Counts as a Strong Result

A strong result is not necessarily:

> XGBoost accuracy = 99.8%

A strong result looks more like:

> The model achieved a substantially higher PR-AUC than the rules baseline under a time-based split, and the cost-optimized policy reduced expected loss while keeping manual review below the defined capacity.

Or:

> The supervised model performed strongly on known fraud types but degraded on a held-out fraud scenario; adding the anomaly score improved recall for that unseen pattern.

Or:

> Calibration materially improved the relationship between predicted probabilities and observed fraud rates, making risk scores more operationally interpretable.

These are real analytical conclusions.

# 62. External Validation

If practical, use a public fraud benchmark as a secondary experiment.

Potential benchmark families include publicly available transaction-fraud datasets such as:

- IEEE-CIS Fraud Detection;
- PaySim.

The goal is not necessarily to achieve state-of-the-art benchmark performance because the feature schema and simulated environment may differ substantially.

Instead, measure the **sim-to-real gap**.

Possible comparison:

```text
Synthetic test PR-AUC = X
External benchmark PR-AUC = Y
Performance gap = Z
```

Then investigate why the model transfers poorly or well.

This is much more credible than claiming the synthetic simulator represents the real world perfectly.

---

# 63. Sim-to-Real Validation Design

Possible approaches:

## Approach A — Train synthetic, test external

This directly tests transferability.

## Approach B — Train external, test synthetic

This tests whether real-data-learned patterns generalize to simulated behavior.

## Approach C — Fine-tune / recalibrate

Use a small external validation set for calibration or threshold adjustment without hiding the original transfer gap.

All results must explicitly state the differences in feature schemas and labels.

# 65. Risk Policy Design

The project should make it clear that the ML model predicts risk, while the **policy converts risk into an action**.

For example:

```text
Probability / score

< 0.20  → APPROVE
0.20–0.60 → STEP-UP VERIFICATION
0.60–0.90 → MANUAL REVIEW
> 0.90 → HOLD / BLOCK
```

These are example categories only.

The final thresholds should be selected through the cost-optimization experiment.

---

# 66. Decision Policy Under Analyst Capacity

A more advanced policy can prioritize the review queue by:

```text
expected_loss_avoided
---------------------
review_cost
```

This approximates which transactions provide the most economic value per unit of analyst capacity.

Alternatively, rank by:

```text
fraud_probability × transaction_amount
```

then compare the result against the calibrated-risk-only policy.

This can become a separate policy experiment.

# 81. Key Tradeoffs to Document

The project should explicitly discuss tradeoffs.

## Precision vs Recall

Higher recall usually increases false positives.

## Fraud Loss vs Customer Friction

More aggressive blocking can reduce fraud while annoying legitimate customers.

## Review Capacity vs Detection

Investigators cannot inspect unlimited alerts.

## Model Complexity vs Explainability

XGBoost is more expressive than Logistic Regression but requires explainability tooling.

## Synthetic Realism vs Reproducibility

A highly complex simulator may appear realistic but become difficult to validate or reproduce.

## Benchmark Transfer vs Feature Compatibility

External validation is valuable but may require schema adaptation.

## Real-Time Latency vs Feature Richness

Complex behavioral features may improve prediction but increase inference cost.

These tradeoffs are valuable interview material.

# 87. Development Principle

The order of work matters.

Do not start with the web app.

Do not tune XGBoost before validating the data.

Do not optimize thresholds before probabilities are calibrated.

Do not trust feature importance before leakage tests pass.

Do not claim anomaly detection helps until the unseen-fraud experiment proves it.

Do not publish resume numbers until the final test set is locked.

The correct progression is:

```text
Data realism
    ↓
Feature correctness
    ↓
Evaluation correctness
    ↓
Model performance
    ↓
Decision optimization
    ↓
Explainability
    ↓
Deployment
```
